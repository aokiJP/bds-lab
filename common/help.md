## tests
tests.txt: one command per line (anything `run` accepts, incl. @A actions, js, until, wait), expectations below it:
`= exact line` `~ regex` (JS; a leading `(?i)` = ignore case) `! substring must be absent` `!~ regex must be absent`. `## title` starts a section: its expectations see all output since the title (late events count). `clock +1d|+3h|+90m|-30s`: the addon's Date (Date.now, new Date) runs that far ahead from then on, kept over /reload and restart (a daily bonus, a weekly reset; `time set` is the game's sky, not Date). Sections run in order in one world: what one leaves (items, cooldowns, saved data, scores, joined players) the next sees. `#` comment.
A line starting with `E ` that no expectation matched fails the test. `test other.txt` runs another file. The last run's summary is .lab/report.json.
Timing: prefer `until <regex> [ms]` over `wait`. Events from a tick later still land in the section. Each `until` counts as a check (PASS n/m); a tests.txt with no check at all fails (it could never catch a bug).
Forms: `@A form <index|button text>` for buttons; a custom form takes one value per input in order, `form ["text", true, 2]`, a dropdown or step slider also by its option's text (`form ["緑"]`), and a form with one input without brackets (`form 緑`). An answer that does not fit is an `E @A form: ...` line naming the form's inputs.
Other BDS builds: `test --bds 1.26.45.1,1.26.36.1` or `test --matrix` (current + the 2 previous families; `bds --list`). Each build runs in its own cache (.lab/v/<ver>), the real client speaks its protocol. To pass there: header.min_engine_version (bp and rp) no newer than that build, and stable module versions it offers (the error lists them); beta module versions exist per build only.

## debug
Mojang's script debugger protocol is attached to every run from the world's first tick (no addon edits, nothing to install).
`trace <file:line> [expr ...] [xN]`: file = src/foo.ts (TypeScript, mapped through the build) or main.js / bp/scripts/foo.js. First hit prints every local and module (closure) variable, later hits only the ones that changed; unchanged hits are counted, not printed. With exprs only those are evaluated in that frame (any JS, e.g. `player.location.y` `list.length`). xN = stop after N hits (default 20).
`-t file:line` on run/test/up sets a trace before the addon's first line runs (startup code).
`trace err`: every throw in the addon stops and prints `X <file:line> <error> | <variables>`. Caught exceptions stop too (each pause is a few ms: turn it off after use).
`cov on` then `cov` (live), or `test --cov`: which source lines ran (breakpoint on every line, removed at its first hit). The test pass/fail comes from a normal pass; coverage is a second pass.
`node lab.mjs why ["<section>"]` does trace err + events + cov for a failing section in one run and reads them for you (`help quality`).
Each stop pauses the whole server briefly; timing-sensitive checks belong in runs without traces.

## model
Entity/attachable models (rp/models/entity/*.geo.json, per-face or box UV): `render <ns:entity|geometry.id|file> [--anim <animation id>[@sec]] [--views front34,side,rear34,top,front,rear,left,low34] [--tex png]` draws it the way the game does, with its texture and pose. `check` lints every geometry: W collapsed cube, z-fight, UV off the texture, unequal plate faces, duplicate cube. Look at vanilla first: `render minecraft:<mob>`, `sample rp/models/entity/<name>`. The procedure and its proven rules: `skill bds-models`.
How the game draws (learned against the game by iMasterProX/mcbemodelingmasterAI):
- mirrored in x: a cube's "east" UV shows on its low-x JSON side (the world's east after the mirror). Never decide sides from the JSON: render.
- rotation [rx,ry,rz] = right-handed (-rx, ry, -rz), X then Y then Z, about the pivot (a cube with no pivot: its centre). Animation rotations ADD to the bind pose.
- no stair steps: curves are tilted boxes joined corner to corner; where a width steps, splay a box out to the wider corner.
- no two faces on one plane (z-fight): move one 0.02-0.05, then paint the thin step so it continues its neighbour.
- thin things (wing, fin, leaf, cloth) are ONE zero-thickness plate cut out by transparent texels (material entity_alphatest), both faces painted by position.
- one bone per moving thing, pivot at the real joint; model a moving part open, fold it with the bind pose, render every pose (--anim id@0, @end).
- texture nobody can see: one texel; texture meant to be seen: visible from where the player looks.

## auto
The autopilot: the AI runs bds-lab by itself. Each tick it senses work with no tokens (a unit whose last test failed → repair · maintain due → upkeep · an open issue labeled `auto` → issue · TASK.md changes not released → release · `- [ ] <request>` in auto/BACKLOG.md → backlog · `- [ ] lab: <change>` → lab (it changes the engine itself) · never playtested → playtest · not hardened in 14 days → harden · every few tasks → reflect (rewrites its backlog, condenses auto/LESSONS.md) · a thin backlog → invent (new addon ideas)), ranks them (value × the success rate auto/ledger.jsonl has seen for the kind × cost; a target that failed waits 2^n hours, 4 failures give up), the AI picks one with its reason, does it, and keeps it only if the lab's checks pass: `go` for a unit, the gate (auto/policy.json `gate`: offline tests that passed before must still pass) for the engine; then a second AI reviews the diff (REJECT → put back; a release's version/notes or tests only appended need no reviewer), it is committed and pushed (merge auto|pr|local), a unit is released, a failure becomes a one-line lesson (the newest 12, ≤1,500 chars, reach every later make: LAB_MAKE_CONTEXT). The AI is asked to choose only when the scores are close (a broken unit or twice the next score: no question). Each kind changes only its part (a unit task its unit, maintain also common/data, share VERSION/CHANGES.md, the engine agent the lab): the rest is put back; the floor fails the task. maintain/harden/release keep what passed even when the run fails (one unit fixed of three is merged as partly).
`node lab.mjs auto` (the queue) · `auto run [--ticks n|--forever] [--dry] [--via v] [--model m]` (the lab calls the AI) · `auto next` / `auto done <id> ok|fail "<lesson>"` (you are the AI: one task at a time; `done` gates an engine task and puts it back if it fails) · `auto gate` (the offline gate, side by side; `--all` every offline test, `--jobs n`) · `auto log [n]` · `auto plan` (work this run or not, and for which labs: the schedule asks it before its set-up) · `auto schedule hourly|daily|off`. GitHub: .github/workflows/auto.yml runs a tick every hour; an hour with nothing to do ends after `auto plan` (no Python, Wine or build tools set up). Without an AI it leaves harden alone too (it asks an AI for what it adds); a failing upkeep waits a day, two, four … a week, and is never given up.
The person's floor (common/auto-guard.mjs; never written by the AI, a change touching it is put back): auto/STOP (`auto stop` / `auto resume`), auto/policy.json (dailyTokens, taskTokens, merge, push, release, review, kinds, gate; `auto policy key=value`).
## sim
`node lab.mjs sim [-a <addon|folder>] [--ticks n] [--json]` = the addon's tests.txt in about a second, with no server: sandbox-be/ (the Script API and player movement measured against BDS, in a virtual world) runs the `##` sections in order in one world, as `go` does (state, items, cooldowns and joined players carry over; `@A join` again prints `@A already joined`). It does `@A join` `@A cmd` `@A chat` `@A jump` `@A form <n|button text|[values]>|close` (a custom form: one value per input, a dropdown by its text too) `@A interact|attack x y z` (useon/dig) `@A walk forward|back|left|right [ticks]` (20 ticks = 4.3 blocks, as measured) `@A goto x z` (a straight line) `@A leave` then `@A join` (comes back with what they had; a miss in a section that moves is `?` UNSURE) `clock +1d` (the scripts' Date runs ahead) `restart` (a fresh load of the scripts in the world the server kept: saved properties, items, tags, blocks, scores; what scripts held in memory is gone; players rejoin, as BDS does) `@A select <item>` `@A use` `@A useon x y z` `@A place <block> x y z` `@A dig x y z` `@A eat` `scriptevent` console commands `wait` `until` (2 s), prints the lab's shapes (`@A <chat>`, `@A form action: title("..") button("..")`, `@A title: ..`, console lines, `E <error>`) and checks the section's expectations. `js <expr>` lines run too (the same helpers: p inv mob hit dim $; not sim()/answer()). Sections with lines it cannot do (@A walk…, js with simulated players) are SKIPPED; a section that passes alone but not after the ones before it says so (an earlier section left state behind; a skipped section before it makes its failure `?` UNSURE); a failure shows the line of src/ that threw and its code; with a beta module or one newer than the sandbox's game a failure is `?` UNSURE (exit 0). A hint for the loop between edits: `go` on the real server decides. sandbox-be/ here is its runtime only (src/ data/ types/); its CLI, tests and calibration tools are upstream: github.com/Au12jp/sandbox-be.

## ts
TS REPL (the utility addon in every live server) driven from here: code runs in the live world at once — no restart, no `/reload`, no `/reload all` — typed by the game's own TypeScript, in TS REPL's context (`world system mc ui player dimension say run console`, `import` from @minecraft/server / server-ui). Start with `node lab.mjs up` (ts starts it if needed); everything goes through BDS's console, which TS REPL trusts as the owner.
- `ts "<code>"` / `ts <file>`: run it now; the last expression is the answer (`= ...`), its console.log lines first, a type error as `E line:col TScode message` (nothing ran). A file is its own slot: running it again removes only that file's last subscribe / runInterval / runTimeout, then sets up the new ones (hot swap). Later logs of those handlers print as `[tsrepl:slot:<file>] ...` in ts, do and watch. `--as <player>` runs as that player (`player`); nobody online: as the server.
- `ts hot <file>...`: the same on every save (a person's loop: editor beside the game; Ctrl+C removes its handlers). An AI runs `ts <file>` after each edit instead.
- `ts stop [<file>|--all]` · `ts check <file|code>` (types only) · `ts state` (tick, players: where, tags; saved scripts) · `ts list` · `ts rm <name>`.
- `ts save <file> [--name n]`: kept in the world as a TS REPL script (also after a restart), trigger from its first lines: `// @on <afterEvent>` (playerBreakBlock, entityHurt, itemUse ... TS REPL's list), `// @every <ticks>`, `// @join` (the first join after a start), none = by hand. Live at once; `// @command ns:name` and `// @startup` wait for the next start.
- `ts pull|push [<dir>]` (default ts/): saved scripts ↔ files, the trigger as that header. `ts sync [<dir>] [--for s]`: both ways while it runs — save in your editor and it is in the world; change it in TS REPL's in-game editor and the file follows; changed on both sides: the game's is kept, yours goes to `<name>.local.ts`.
- `ts watch [--for s]`: what players do (joins, chat, blocks broken / placed / touched, items used, hits, deaths, dimension, game mode) and what the addons print, as it happens: watch a person play your addon (default 30 s when not a terminal).
- `ts join`: how a person joins from their own Minecraft (Servers → Add Server: 127.0.0.1 or this PC's network address, port 19132 when free; online-mode off, everyone operator; `/function tsrepl_start` opens TS REPL in the game). The live server stays up while someone is on it.
- `ts try "<code>"|<file>`: the same code and names in sandbox-be, no server (~1 s; what it cannot do is said).
- `ts promote <file|saved script> <unit>`: a new addon unit (bds/addons/<unit>/src/main.ts) from it: an `@on` script subscribes to that event, `@every` runs on an interval, `@join` on the first spawn, one that leaves handlers sets them up when the world loads, a one-off runs on `/scriptevent <unit>:run`. Then tests.txt and `go`.
Examples: ts/examples/ (hello, heal, block-log, kills, clock, welcome). The addon's own context (its module-level state is not reachable, its dynamic properties are): `do 'js <expr>'`. A person who joins gets TS REPL (owner tags, its console item). What stays an addon's: custom commands and components (registered at startup: `do` reloads), the addon's own dynamic properties (TS REPL has its own). Limits: 2 s per run, 20,000 characters, first run ~5 s (the compiler loads). TS REPL's changes for this: bds/addons/ts_repl/lab/patch.py (TASK.md).
## bb
bedrock-binary (bds-lab/bedrock-binary) reads this lab's own BDS binary (~5 s, no download; a Windows lab fetches the Linux build of the same version once and keeps only what it read) and keeps the result per version in <lab>/.lab/bb/. What it holds that no document says:
- `bb`: the summary — packet ids, enums (how many have their real type name), commands and how many Mojang's docs leave out, WSS event types, the script modules the server knows (their versions: the lab's own measurement), and what changed since the last version it read.
- `bb packets [name|id|0xNN]`: packet ids of this BDS, read from each packet class's getId() in the code (the MinecraftPacketIds enum's order is not the ids: removed ids leave gaps, 200-299 are reserved, newer packets are out of order); checked against Mojang's protocol docs when `proto` has fetched them; an enumerator with no class says so (`proto <Packet>` = its fields) · `bb enum [name]`: an enum's values with their ids (ActorDamageCause, ActorType, Connection::DisconnectFailReason, ItemStackNetResult ...; no name = the list) · `bb strings <word> [--dead]`: identifiers in the binary (--dead: nothing uses them).
- `bb commands`: the commands the docs leave out, each tried once on a fresh BDS here: runs (listd ...), has it with arguments (querytarget, gettopsolidblock, serveridentity ...), or not on this server (Education / client / other builds). `doc /<command>` says the same for one of them. sandbox-be knows those as "not reproduced", not "unknown".
- `bb diff [--short] [<a.json> <b.json>]`: two versions (default: the last one read before this BDS): new / removed / renumbered packets, commands, enum ids that moved (what breaks a protocol client silently). `upkeep` prints the --short line after every Minecraft update.
- `bb site`: the searchable page and metadata JSON (Mojang's bedrock-samples metadata shape) in <lab>/.lab/bb/site/ · `bb apk [<folder>]`: the Android client's library (app/.lab/apk from `app apk fetch`) · `bb <command>`: bedrock-binary's other commands (`bb list`; bedrock-binary/README.md).
## schema
Every build checks each bp/ and rp/ JSON file against @minecraft/bedrock-schemas (common/schema.mjs; installed once into the lab cache at the calibrated version). Calibrated on all 7,000+ vanilla files: what vanilla itself breaks is never reported. `E <file> <json path>: must be integer (got "4")` = a type / value / required key wrong where vanilla shows the schema is right, or what a real BDS refuses and the schemas omit (block light 0..15, max_stack_size 1..64, `unlock` in 1.20+ crafting recipes): the definition would not load, fix it. `W ... unknown key "x": did you mean "y"?` = the game ignores that key silently (a typo); `W ... must be ≤ 64` = ranges, patterns. Items are checked against the component forms (`doc minecraft:<component> item`). `LAB_SCHEMA=off` skips it. Maintainers, after a Minecraft update: `node common/schema.mjs calibrate <bedrock-samples> <schemas dir> [bp:<dir> rp:<dir>]`.
## deploy
`node lab.mjs deploy <your BDS folder> [<unit> ...] [--world <name>] [--dry] [--undo]` = put addons on a BDS of your own and change its settings so they work, as the lab does for its test servers: the utility addons (common/data/samples.json `utility`: TS REPL) and the units named become world packs (worlds/<level>/behavior_packs|resource_packs + world_behavior_packs.json / world_resource_packs.json, matched by pack UUID: a second deploy replaces, never doubles), config/default/permissions.json allows every @minecraft/* module they ask for (BDS's default leaves out @minecraft/common and @minecraft/server-net: such an addon does not load), a pack on beta modules turns on the Beta APIs experiment in level.dat (other experiments and tags kept; no level.dat yet: start the server once, then deploy again). ## upkeep
Not sure what to run: `node lab.mjs status` (where things stand, the next command) · `upkeep --check` (what is wrong, changes nothing) · `upkeep` (fixes it). Disk full: `clean`.
Start here: `node lab.mjs upkeep` = everything, in order, one screen: 1 health checks (repairs what is safe) · 2 cleaning (what can be rebuilt) · 3 every lab on the newest Minecraft / Endstone / LeviLamina, every unit tested there, what broke fixed · 4 what changed, what still fails, the one next command. `--check` changes nothing (what it would do, whether a newer version is out) · `--auto daily|weekly|off [--at HH:MM]` this machine does it by itself (results to LAB_NOTIFY_WEBHOOK) · `--no-ai` · `--lab bds|end|ll|all`. A network failure is said apart, never as a problem of the lab. On GitHub, .github/workflows/latest.yml does step 3 for every new release and opens one pull request; the autopilot does `upkeep` once a day.
The tools under it, for one thing at a time: `maint [--fix] [--online]` (step 1) · `clean [--dry] [--deep]` (step 2) · `maintain` (step 3, below) · `flaky` · `apidiff` · `undo`.
After a Minecraft update, by hand: `node lab.mjs maintain [--lab bds|end|ll|all] [-a u1,u2] [--to latest|preview|current|<ver>] [--dry] [--no-ai] [--no-limit] [--pr]` moves the lab to that release, tests every unit, and for each broken one: autofix (`mode beta|stable`: the module versions this BDS accepts, no AI) → AI patch (`make -a <u> --until test` with the failing lines and the unit's part of the API diff; a patch that edits an old tests.txt section is refused) → limit (features.json: the features whose sections fail are switched off). Else BROKEN: put back, the attempt kept as a checkpoint. A release the lab cannot run yet (the real client does not speak it): WAIT, the lab goes back to its BDS. Features switched off earlier are tried again first (RESTORED). Results: TASK.md `## Maintenance`, `<lab>/.lab/maintain/report.md` and `<version>/<unit>.diff`. `--to preview` is a dry run unless `--apply`.
Fixing a unit for a new version yourself: `node lab.mjs apidiff [<from> <to>] [--preview] [--stable] [--all]` = what @minecraft/server removed/changed/added/made stable and the file:line of every unit that uses it (npm types, no server). A feature that cannot work on this version: features.json `{"features": {"<name>": {"tests": ["<## title>"]}}, "off": {"<name>": "<why>"}}` and wrap its set-up in kit `feature('<name>', () => {...})` (plain JS: `import './lab_features.js'` first; `globalThis.LAB_FEATURES_OFF`); its sections are skipped. Never edit an old test to pass.
Every day by itself: `upkeep --auto daily` (all four steps; `maintain --schedule daily|weekly|off [--at HH:MM]` = step 3 only; cron / Task Scheduler, log in bds/.lab/maintain/scheduled.log). A Minecraft newer than bedrock-protocol: real players borrow its newest packets with the server's protocol number (Mojang's protocol docs, then walked until BDS lets them in), so tests run on a preview on day 0; `LAB_BORROW=0` refuses instead.
A failure that passes on a second fresh run is FLAKY (no AI); `node lab.mjs flaky [-a u] [n]` runs the tests n times and names the sections that pass only sometimes. A beta unit that also passes on stable modules is moved to stable (PROMOTED; `--no-promote`). `--with-preview` on a schedule also checks each new preview once (`--to preview --only-new`). Health: `node lab.mjs maint [--fix] [--online] [--only a,b]` (temp, locks, disk, secrets, leaked tokens, shared pack UUIDs, a stale kb.json, files an earlier release dropped that an older `update` left, the version lists...; maintain runs the quick ones first). What broke it and when: `help quality` (bisect).
`node lab.mjs release [-a u]` = go DONE → version +1 → CHANGELOG.md from TASK.md → .mcaddon → ship.
`node lab.mjs undo [-a u]` puts back the newest checkpoint (make and maintain take one first; `undo --list`, `undo <id>`, `checkpoint "<label>"`). `node lab.mjs watch [--check|--go|--live]` reruns on every save.
## import
A person's addon (fix, update, finish): `node lab.mjs import <file.mcaddon|.mcpack|.zip|folder> ["<what they asked>"] [--name n]` (paths from where you are) → bds/addons/<name>/ with bp/ rp/ as they were, the request in TASK.md, `imported.json` (the versions it came with), and the brief: packs and module versions (✗ = not in this BDS: a beta is only in the BDS it was made for, stables carry over), the ways in (custom commands, chat words like `!home`, script events, items the code checks, events with file:line), forms, the commands it runs, whether it saves anything (no dynamic properties = everything is lost on restart), and the audit: its code type-checked against this BDS's stable and beta modules, every use that breaks there at once (removed/renamed members with the line), and which `mode` needs fewer changes. tests.txt starts as a draft that runs each way in once (an unexpected E line fails it), so the first `go` shows every crashing path, not one per round; add what the request wants under each section. `node lab.mjs brief` prints the brief again (after a `mode` change: what still breaks). Plain JS stays plain JS. The first `pack`/DONE after import goes one patch version up with the same UUIDs, so the person's worlds and players' clients take it as an update.
## colony
People's distributed worlds and addons from Crafters Colony (minecraft-mcworld.com), into the lab: `node lab.mjs colony search <words> [--cat <id|name>] [--sort dl|rating|weekly|monthly|all]` (newest first through the site's index; a sort, or an index that does not answer, through its own list page) · `colony new` (the newest posts, one request) · `colony cats` · `colony show <post>` (author, category, the info table, its download buttons) · `colony get <post> [--type mcworld|mcaddon|mcpack|zip]` (through the site's own button or a known file host: Dropbox, Google Drive, MediaFire; checked by CRC, then inspected) → .lab/colony/<post>/ · `colony inspect <file|post>` (Bedrock or Java world, addon; level.dat; bundled packs; `--list` the entries) · `colony repack <file>` (a zip with the world one folder down → a proper .mcworld) · `colony convert <file> --chunker <jar>` (Java → Bedrock with Chunker CLI) · `colony install <file|post> [--dir <minecraftWorlds>]` (Windows: the GDK folder %APPDATA%\Minecraft Bedrock\Users\<n>\… first, then the old UWP one; close the game first) · `colony packs <file|post> [--sim]` (each bundled pack; --sim runs the behavior packs in the sandbox, an old @minecraft/server version read as the newest the sandbox has, said) · `colony import <file|post> ["<request>"] [--pack p]` (the addon, or the world's behavior pack with the resource pack it depends on, as a unit: then `go`) · `colony voxel <file|post> [--radius n] [--height n]` (the terrain around spawn as a sandbox course: LevelDB tables and logs read as Mojang's leveldb writes them, SpawnY 32767 = the ground there; a post's page gives it its title, players and the time to clear it as the deadline). <post> = the number in its URL, or the URL. Read-only and polite: a request every 2.5–5 s, at most 80 an hour across runs, pages kept an hour (`--fresh`); it never likes, counts, comments or posts. A zip whose names climb out of the folder (../) is refused before anything is written; Shift_JIS names of old Japanese zips are read as Japanese.
## skills
The lab's know-how as skills any AI can read (skills/<name>/SKILL.md: name and description up top, the format Claude Code and Codex load; `node lab.mjs skill` lists them, `skill <name>` prints one: read the ONE that fits, each costs tokens on every later turn; `bds-addon-master` routes). Every rule line comes from skills/knowledge.json, where each rule has its evidence: a probe (skills/probes/<id>: a tiny addon + tests.txt that shows the fact on the real BDS), an offline test, or a measurement; `skill build [--check]` writes the rule lines into the SKILL.md files (the gate fails when they drift).
How they grow (each step costs no tokens unless it says so): 1 experience — every test/go records the failures the last edit made go away, with the fix/hint lines the lab printed (<lab>/.lab/episodes.jsonl). 2 reflection — `skill learn` turns recurring ones (and auto/LESSONS.md) into candidate rules; candidates are not in SKILL.md. 3 proof — a candidate becomes a rule only with evidence: write a probe or point at a test, `skill promote <id> --evidence probe:skills/probes/<id>` (or test:<file> / measured:"<what>"). 4 re-checking — `skill verify [id|probe|all]` runs each rule's evidence again; upkeep does it on every new Minecraft: a rule the new server contradicts becomes disputed and leaves SKILL.md until fixed. 4b at the moment it is needed — a rule with a `match` regex prints its one line (`  rule: … (\`id\`, skill …)`) under the E / W / Q / ✘ line it explains, once per run (LAB_RULE_HINTS=off: never); learn counts its misses — how often its failure still happened in units — and flags a rule missed 3× in 2 units: reading it does not prevent it, so make it a check (an E/Q line before the server runs) or rewrite it. 4c from other projects — `skill learn --from <folder | https://github.com/owner/repo>` (cloned once into .lab/skill-sources) reads that project's SKILL.md lines, data/rules.json and data/failure-modes.json and adds the hard rules the lab does not have yet as candidates with source evidence (fragments, questions, lines tied to its own tools and near-duplicates skipped); e.g. iMasterProX/mcbemodelingmasterAI (models), shawtymarco/MCBE-UI and boredape874/mcbejsonuimasterAI (JSON UI). A source rule can be promoted (`--evidence source:<url file>`) and shows [source] in the skill until a test or probe proves it here. 5 selection — `skill bench [--via claude|codex|gemini|anthropic|openai] [--tasks a,b] [--runs n]` (AI tokens) builds the bench tasks with and without the skills (hidden tests decide pass) and keeps a skills version only when it passes no fewer tasks and costs no more than 10% more tokens (skills/history.json). 6 pruning — a skill over 3.2 KB warns at build: split it or `skill retire <id> "<why>"` what no longer helps. One run is an anecdote: compare over several (--runs).
Growth: `skill growth` — the generation (knowledge.json `log`: a line whenever the counts change), how the rules are proven (re-run here / measured once / [source]), candidates, disputed, experience (episodes, failures fixed per unit, older half → newer half: fewer = the skills prevent more), the last bench, and the next rung for each part (a missed rule → a check; disputed → fix; candidates → proof; [source] → a test or probe; never benched → bench).
As prompts (common/skill-forge.mjs; no tokens except the AI's own edits and bench): a skill is also judged whole, the way it works as a system prompt. `skill grade [name|all]` scores each against skills/rubric.json (0-2 per criterion: name, trigger (what + Use when, front-loaded, ≤500 chars), boundary (Not for … use `other`), procedure (numbered steps), example (a real command), rules-why, done (Done when / Report), honesty (what is not verified), budget (500-3200 B), portable (no product tool names or home paths), focus (no overlap with a sibling), no-repeat (nothing AGENTS.md already says), grounded (every command and path exists), evidence (rules re-run here), routed (the master names it, the router finds it)); each criterion has its source (SkillsBench arXiv 2602.12670, Codex skill docs, the three reference repositories) and its fix. `--ref <dir|https://github.com/owner/repo>` grades a reference collection on the portable criteria and, where theirs scores higher, quotes the line that earns it (the rubric is ours: scoring above a reference is not proof; bench is). `skill route "<request, any language>"` names the skill to read and the words that matched (BM25 over name, description, skills/<name>/triggers.txt, body; Japanese by katakana words and kanji pairs); `--eval` scores it on skills/routes.json (dev cases may be read; held-out ones measure whether a change generalises and are never listed or copied).
Writing and refining: `skill new <name> "<what it does. Use when …>"` writes SKILL.md from the shared shape + triggers.txt, as a draft (SkillsBench: skills a model writes for itself averaged -1.3pp, so a draft is not trusted yet). `skill refine <name|weakest>` snapshots it and prints the brief: each weak criterion with how the best reference skill does it, rules still missed, candidates, requests routed wrong, how often it is read; edit, then `skill refine <name> --done` keeps the edit only if no criterion, no other skill and no routing case (dev or held-out) got worse, under 3200 B with the rules block intact — else the old files come back with the reason (`--revert` by hand). `skill bench --without <name>` (AI tokens) builds the bench tasks with all skills vs all but that one: a draft no worse with it becomes kept (skills/grades.json). Every grade change is a generation in skills/grades.json (scores per skill, routing, rubric version, why).
Growth, three layers (`skill growth`): L1 rules (the ladder above), L2 skills (grade, routing first-pick dev / held-out, refinements kept / reverted, drafts, reads per skill and failures fixed per unit with vs without reading it: .lab/skill-reads.jsonl), L3 the rubric itself — each bench records the grade it ran with, and growth says whether grade and bench pass rate move together (a rubric that does not predict results gets rewritten); a mean grade at 90%+ means the rubric no longer separates skills: add a stricter criterion (rubric version + 1, as v2 added no-repeat) from a bench failure or a reference.
More (common/skill-evolve.mjs; the whole system in Japanese: skills/GROWTH.md): `skill new <name> "<…>" --like <skill|repo/skill|path>` borrows the sections of a skill that works. `skill refine <name|weakest> --via <claude|codex|gemini|anthropic|openai|auto|"<cmd {prompt_file}>"> [--rounds n]` lets another AI do the edit (one question, no tools: the lab writes the files it answers with) and gates it strictly: an edit is kept only if it raises the grade or the routing, never if it touches the rules block, leaves an only-part open or grows the skill without gain; a reverted try's reason goes into the next prompt; `weakest` picks the lowest score an edit can still raise (evidence is a probe's job, not text) and passes over a skill reverted twice in a row. A manual edit that adds what the grade cannot see (a new command to document): `--done --because "<what it adds>"` (logged). `skill route --eval` also counts requests no skill owns (want []: the router must name none) and lists close calls (right by a hair). `skill compare [--ref …]`: ours and each reference collection per portable criterion (recorded for growth). `skill rubric [mine|calibrate|adopt <id>|retire <id> "<why>"]`: parts most reference skills have and ours lack become pattern candidates (rubric.json `re`: checked as data, no code); calibrate says per criterion whether it still separates skills (a `gate` like name or size is a must) and per candidate whether reference skills that have it score higher on the rest within the same repository (+5pt: adoptable; the same as a criterion or a stronger candidate: redundant). `skill prompt --for <ai> [--budget bytes] [--skills a,b] [--out file]`: one system prompt (the routing list, then whole skills in order of use and grade) for an AI with no skill folder. One AI's part of a SKILL.md: `<!-- only:claude,codex -->…<!-- /only -->` (not in the shared view, the grade or other AIs' copies; `skill <name> --for <ai>` shows it). The autopilot adds a `forge` task (skill refine <weakest> --via auto) when a skill's editable score is under 85% or held-out routing under 80%.
Fewer tokens, nothing lost (v1.18): `skill <name>` prints the reader view — no front matter (the router matched it already), no build markers, no rule ids (the just-in-time `rule:` line names the id), and no rule AGENTS.md already says (knowledge.json `entry`: a phrase of AGENTS.md; if it leaves AGENTS.md the rule shows again); `--raw` prints the file. `skill a b` prints several in one call. `skill route "<request>"` prints the skill itself when one owner is clear (no second call to read it: every call re-sends the conversation; `--list` only names); a catalog skill (a `<!-- catalog -->` line, as in bds-recipes) shows only the 3 lines whose words fit the request (knowledge.json `tags`: the words people use, any language). `skill refine <name> --via <ai> --goal shorter` asks another AI for the same skill in fewer words; kept only when 5%+ smaller with every `code span`, number and rule id still there (or said by AGENTS.md) and nothing else worse; reworded rules go back to knowledge.json by id.
Other AIs and projects: `skill install <claude|codex|gemini|copilot|cursor|windsurf|cline|roo|kiro|opencode|aider|agents|all> [--to <dir>] [--global] [--drafts]` writes SKILL.md folders where each one looks (.claude/skills, .agents/skills for Codex and any agent, .gemini/skills, .github/skills (~/.copilot/skills with --global), .cursor/skills, .windsurf/skills, .cline/skills, .roo/skills, .kiro/skills, .opencode/skills; Aider has none: a routing block in CONVENTIONS.md); Gemini, Copilot and agents also get a routing block in GEMINI.md / .github/copilot-instructions.md / AGENTS.md naming `skill <name>` and `skill route`. SKILL.md stays portable; what one AI alone needs goes in skills/<name>/ai/<ai>.md and is added under "Only for <ai>" in that AI's copy (e.g. bds-models/ai/codex.md). Drafts and lab-only skills (skill-forge) are left out. Run it again after the skills change.
## scratch
Building from nothing, and learning from it (common/scratch.mjs; skill `bds-from-scratch` has the steps for a real request). The lessons are the bench's tasks (bds/bench/tasks.json: a request in a person's words, graded by `level`, and hidden tests), each proven solvable by the reference solution (bds/bench/solution.mjs: never read it while practising) and failing on the empty template (`scratch selftest`, `--real` on the real BDS too).
`node lab.mjs scratch` lists them by level with what this lab passed · `scratch next [--level n]` the next one and how · `scratch show <id>` its request · `scratch check <id>` its hidden tests on bds/addons/scratch_<id> in the sandbox (seconds, a hint), `--real` on the real BDS (the verdict; `clean` lessons also need `check` without E/W) · `scratch stats` first-try passes, checks, per skill, how often the sandbox predicted the real verdict.
The places to learn are the sandbox (sandbox-be: `sim`, `ts try`) and the live world (TS REPL: `ts`, after `up`). What they teach goes back: every check is an episode (`skill learn`); a section where the sandbox and the real BDS disagree on the same code is a gap (`scratch gaps`, `--backlog` files them for sandbox-be: the sandbox learns too); `scratch probe "<code>"` runs the same code in both, AGREE or DIFFER, and `--rule "<rule>" --skill <name>` turns an agreement into a candidate rule with measured evidence (`skill promote <id>`). State: bds/.lab/scratch.jsonl, scratch-gaps.jsonl, probes.jsonl (this machine's, never shipped).
## quality
The loop: go fails → `why` (go runs it itself when what failed names no src/ line; LAB_GO_WHY=off stops that) (then fix); go DONE → `gaps`, `mutate`, `chaos` → a `##` section for each finding → go. No tokens; each is a few runs on fresh servers; the unit is never changed (only `--append` adds to tests.txt).
`node lab.mjs why [-a u] ["<section>"]`: the section (default: the first that failed last) runs again after the sections before it, with every throw stopped and printed with its local values, the events, and the lines that ran. It says what came instead of each failing expectation (the lines printed from that command on), where it threw (your line, the code around it, the values; kit frames as `via`), else the line that printed what came instead (a second run stops there for its values) and the line that would print what the test wants (did it run?), the hooks the section uses that never ran (an item/block hook: is its component in the json?), and `next:`. Read it before editing.
`node lab.mjs shrink [-a u] ["<section>"] [--max n]`: the failing section cut to the fewest lines (and sections before it) that still fail the same way: the same error, or the same expectation with the same line coming instead. A player the kept lines still name joins first. At most n runs (12).
`node lab.mjs gaps [-a u]`: one run with coverage: each place of your code no test runs, what runs it, and test lines that reach it (`src/main.ts:33 never ran: /lab:shop → @A cmd /lab:shop · until form · @A form 0`).
`node lab.mjs record [-a u] "<line>" ["<line>" ...] [--title t] [--append]`: what those lines print now, as a section: twice on fresh servers, the same line both times `= line`, one whose numbers change `~ regex`; script errors are named, never recorded; players they name join first. It is what the code does now: check it against the request.
`node lab.mjs chaos [-a u] [steps=30] [--seed n] [--runs n] [--append]`: real players (names tests.txt does not use) play the unit at random — its commands with random arguments and forms answered at random, its items, blocks, menu buttons, the events it listens to, a second player, a restart — until a script error. The steps are cut to the fewest that still cause it, then run after the sections of tests.txt: printed (`--append`: added) only if it fails there too, so it fails until the bug is fixed. Same seed, same play.
`node lab.mjs harden [-a u] [n] [--via ...]` (= `make -a u --harden [n]`; it asks an AI: a person's command): gaps and n mutate bugs are measured first (nothing missed: no AI call); the AI appends `## harden:` sections aimed at them; anything else it changes is put back and old sections stay as they were; a new section that fails on the code is kept out (SUSPECT, printed with its lines: a bug or a wrong test); then the same bugs and the coverage again, before → after.
`node lab.mjs bisect [-a u] ["<section>"] [--good <id>]`: it passed once, it fails now → the unit's checkpoints (make, maintain, mode, add take them) are tested back from the newest, then by halving (a recent break: 2 runs); prints the first that fails after the last that passed and the diff between them. The unit is left as it was.
`node lab.mjs mutate [-a u] [n] [--all]`: small bugs (=== ↔ !==, >= → >, && → ||, true → false, a call left out, a number +1) go into your code one at a time and tests.txt runs on each; each bug no test notices is an S line `file:line change`: add a section that checks what that line does. Lines no test runs come first (as gaps prints them) and get no bug. n = server runs (default 6).
`node lab.mjs i18n [-a u]`: the lines each language lacks, with the text another has; `i18n <lang> "key=text" ...` writes them (no .lang to open); `i18n --ai` fills them with one small AI call; `--add zh_CN` adds a language.
`node lab.mjs scan [-a u | <file.mcaddon>]`: what an addon could do (HTTP out, /op /kick /ban /transfer, eval, obfuscated code, the watchdog cancelled, a command built from a player's text); `import` scans by itself. go's QA says your own command lines built from a player's name or text (S).
`node lab.mjs optimize [-a u] [--apply] [--prune]`: PNGs smaller with the same pixels and design/OS files left out (pack does both to the .mcaddon by itself), textures nothing names (--prune).
By themselves: an unedited old src/kit.ts becomes the newest kit at the next build (a T line; `undo` goes back). QA: script time too high → the Q line names the functions and lines it goes to (profiled with 3 players). go on a beta unit that cannot move to stable: the beta-only APIs that keep it there (S). maint: units sharing pack UUIDs (`--fix` renews the newer), kb.json for an older BDS (`--fix` rebuilds it), `--online` the version lists; maintain refreshes those after an update.
## login
Sign-ins for a person (not for an AI): `node lab.mjs login [status|github|google|microsoft <name>|ai]`. Accounts come from the environment, `.env.local`, `.env` (template: `.env.example`), else they are asked at the terminal; a real browser opens and the lab fills in the address, password, TOTP (`*_TOTP_SECRET`) and device code. No screen: a hidden browser, codes asked at the terminal. `GH_TOKEN` in .env: GitHub without a browser. Passwords never enter the environment (`common/secrets.mjs`, `common/auth.mjs`; test: `node tests/login-offline.mjs`).
