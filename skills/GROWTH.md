# スキルが育つ仕組み（体系）

bds-lab のスキルは、どの AI でも読める SKILL.md です（先頭に name と「いつ使うか」、中身は手順と規則）。ここでは、それが**自分で育つ仕組み**を層ごとにまとめます。どの層も「測る → 直す → 悪くなったら戻す → 記録する」の同じ形をしていて、トークンを使うのは AI が文章を書くところとベンチだけです。

## 原則

1. **測れないものは育てない**：どの変更も、採点・振り分け・テスト・実機のどれかで前後を比べ、良くなったときだけ残します。
2. **AI が自分で書いたものは信用しない**：SkillsBench（arXiv 2602.12670）では、AI が自分用に書いたスキルは平均 -1.3pt、人が選んだものは +16.2pt でした。AI が書いたものは「下書き」で始まり、証拠が付いて初めて正式になります。
3. **物差しも疑う**：採点は正規表現の物差しなので、AI はそれをごまかせます（実際に起きた例は下の L3 を参照）。物差し自体も、参考のスキル集とベンチで確かめます。
4. **全部の AI で同じ本文**：本文は製品名を書かない共通の文章にします。ある AI だけに要ることは `<!-- only:<AI名> -->…<!-- /only -->` か `skills/<名前>/ai/<AI名>.md` に分けます。

## 層

| 層 | 育つもの | 測るもの | 動かすコマンド | 戻す仕組み | 記録 |
|---|---|---|---|---|---|
| L0 体験 | 失敗と直し方、読まれた回数 | test / go のたびに自動 | （自動）、`skill note "<一行>"` | — | `<lab>/.lab/episodes.jsonl`、`.lab/skill-reads.jsonl`、auto/LESSONS.md |
| L0+ 一から作る | 何も見ずに作る力、サンドボックスの正しさ | 等級つきの課題の隠しテスト（サンドボックス → 実機）、同じコードでの両者の食い違い | `scratch next` → `scratch check <id> [--real]`・`scratch probe`・`scratch gaps` | 課題そのものを `scratch selftest --real` で証明（参照解は通り、空の雛形は落ちる） | bds/.lab/scratch.jsonl・scratch-gaps.jsonl・probes.jsonl |
| L1 規則 | スキルの規則 1 行ずつ | 証拠（probe・テスト・ユニット）を実機で再実行 | `skill learn [--from <URL>]` → `skill promote <id> --evidence …` → `skill verify` | 実機と食い違えば disputed で SKILL.md から外れる | skills/knowledge.json（`log` が世代） |
| L2 スキル | SKILL.md の本文・説明文・triggers.txt | `skill grade`（rubric の各項目）、`skill route --eval`（振り分けの正解率、held-out は見せない） | `skill new [--like]` → `skill refine` → `--done`（`--via <AI>` で別の AI に任せる） | どの項目・どの他スキル・どの振り分けが悪くなっても自動で元に戻す。長くなったのに良くなっていない編集も戻す | skills/grades.json（世代・採用 / 差し戻し・理由） |
| L3 物差し | skills/rubric.json の採点項目 | 参考スキル集との比較（`skill compare`）、同じリポジトリの中での差（`rubric calibrate`）、ベンチとの一致 | `skill rubric mine` → `calibrate` → `adopt` / `retire` | 項目を足すのは「同じリポジトリの中で、それを持つスキルほど他の項目も高い（+5pt 以上）」かつ「既存の項目と同じではない」ときだけ | rubric.json の `version` と `about` の履歴、候補の `calibrated` |
| L4 選択 | スキル一式・一つのスキル | ベンチ（隠しテストで合否）：全スキルあり vs なし、あり vs そのスキルだけ抜き | `skill bench --via <AI> [--without <名前>]` | 悪くなれば WORSE（戻すか退役）。下書きは「抜くと悪くなる」で正式に | skills/history.json（そのときの採点も記録 → L3 の妥当性） |
| L5 自動運転 | 上の全部 | 自動操縦が弱いスキルを見つける | `auto` の forge タスク（`skill refine <弱いもの> --via auto`） | auto の範囲制限（そのスキルのファイルと grades.json だけ）とゲート | auto/ledger.jsonl |

## 学ぶ場所：サンドボックスと TS REPL（v1.19）

規則やスキルの材料は、人のアドオンを直す（保守）だけでなく、**一から作る**ことからも集めます。そのとき試す場所は 2 つです。

- **sandbox-be**（`sim`・`ts try`）：実機で測った仮想世界。1 秒で答えが出るので、作りながら何度でも試せます。
- **TS REPL**（`ts`、`up` の後）：生きた本物の世界で同じコードを動かします。

`scratch probe "<コード>"` は同じコードを両方で動かし、一致すれば「測った証拠」として候補規則にでき（`--rule`）、食い違えばサンドボックスの宿題として記録します（`scratch gaps`）。課題の隠しテストでも、同じコードでサンドボックスと実機の判定が分かれた節は食い違いとして残ります。こうして、スキル（AI の手順）とサンドボックス（AI の練習場）の両方が、本物の BDS を基準に育ちます。

v1.19 で実際に起きたこと：課題を実機で証明する途中で、サンドボックスがプレイヤーのチャットを全員宛ての 1 行として出していたことが分かり（実機は各プレイヤーに `@B chat <A> 本文`）、sandbox-be と sim を直し、規則 `test-broadcast` を広げて probe を実機で再確認しました。

## 一巡の流れ（AI がやること）

1. `node lab.mjs skill growth`：いまの世代、各層の状態、次の一歩。
2. 弱いスキルがあれば `skill refine weakest`（または `--via <AI>`）。その AI 向けの指示書（ブリーフ）には、弱い項目、参考で 2 点を取っている実際の 1 行、見逃された規則、誤った振り分け、僅差の振り分け、前回戻された理由が並びます。
3. 物差しが頭打ち（平均 90% 以上）なら、`skill compare` → `skill rubric mine` → `skill rubric calibrate` を回します。adoptable が出れば `adopt`、出なければベンチだけが基準を上げられます。
4. 新しい依頼に既存のスキルが合わなければ、`skill route` で重複を確かめてから `skill new <名前> "<説明>" --like <手本>` → refine。
5. トークンを使ってよいときは `skill bench --via <AI> --runs 3`（L3・L4 の判定）。

## 実際に起きたこと（v1.16–1.17）

- 第 1 世代は平均 81%、振り分けは dev 76%・held-out 36% でした。refine と triggers の追加で 96% / 100% / 95% になり、rubric v1 が頭打ちになったので v2 で「AGENTS.md の繰り返し」を足して基準を上げました。
- **物差しのごまかし**：別の AI（`refine --via claude`）に master を磨かせたところ、規則に理由が無いという項目を満たすために、根拠の無い「(when missed: …)」を 12 か所足しました（+35% のバイト数、点は変わらず）。当時のゲートは「悪くなっていない」として残してしまいました。手で戻したうえで、次の 3 つを入れました（rubric v3）。
  - 硬い規則が無いスキルは「理由が要らない」ので 2 点にする。
  - 証拠は文章では上げられない項目として印を付ける。
  - AI に任せた編集は何かが上がらないかぎり戻す（`--strict`）。長くなっただけの編集も戻す。
- **戻された理由を次の試行に渡す**：bds-content は同じ失敗（他のスキルの依頼を奪う）を 6 回続けていました。戻された理由をブリーフと次のプロンプトに入れたところ、次の 1 回で採用されました。2 回続けて戻されたスキルは、`weakest` が飛ばします。
- **参考から項目を増やせるか**：jsonuimaster の 75% のスキルにある `## Contract`（Input / Output / Success）は、全体で見ると +10pt と効いて見えました。ところが同じリポジトリの中で比べると +2pt しかなく（もともと良く書かれたリポジトリだっただけ）、採用しませんでした。

## まだ測れていないこと（正直に）

- 一から作る課題（18 個）は、参照解と空の雛形で課題そのものが正しいことは実機で確かめましたが、AI が課題を解いて実際に力が伸びるか（初回で通る率が上がるか）は、まだ回していません（`scratch stats` がその数を出します）。

- スキルで AI のアドオン作りが実際に良くなるかは、ベンチ（AI のトークンが要る）をまだ回していません。L3（採点が結果を予測するか）は、ベンチ 3 回でようやく最初の判定が出ます。
- 振り分けの held-out は、スキル側の言葉と同じ時期に同じ AI が書いた部分があり、完全には独立していません。v1.17 で足した 5 件は、調整を終えてから書いたものです。
- 物差しは、ここで参考と SkillsBench から書いたものです。参考より点が高いことは「その形に沿っている」ことしか示しません。
